# Changelog

## Unreleased

## 0.5.1 — 2026-11-15

### Added
- Examples: `examples/hello.nim` (a server and a client in one process, no generated code), `examples/greeter/` (a service from `hello.proto` through generated code: a server with health and reflection, a client, and both on chronos), and [examples/README.md](examples/README.md), a tutorial with what every command prints.
- `tools/build-nghttp2.sh`: downloads nghttp2 1.68.1, checks its SHA-256 and builds it into `deps/nghttp2` of the clone, without root. Builds inside the repository find it there, or where `NGHTTP2_PREFIX` points; `-d:nghttp2Prefix` on the command line still wins. A program that uses the installed library is not affected.
- `tests/texamples.nim`: builds and runs every `nim c -r examples/...` shown in `README.md` and `examples/README.md` and compares the output with the document; where `protoc` is installed it also checks that `hello_pb.nim` is what the plugin generates.
- [docs/README.md](docs/README.md): an index of the documents with the kind of each page.
- [docs/troubleshooting.md](docs/troubleshooting.md): every message of the library with its meaning and what to do; [docs/faq.md](docs/faq.md); [docs/production.md](docs/production.md), a checklist before a server faces real clients; [docs/supported-versions.md](docs/supported-versions.md).
- `tests/tdocs.nim`: fails when a message the library can raise has no line in the troubleshooting page, makes 17 common failures happen (a closed port, TLS against plaintext, a wrong CA or name, a missing client certificate, a full server, a message over the limit and others) and compares their text with the page, compares the supported-versions page with `nimgrpc.nimble`, the CI workflow and the source, and checks that the index lists every page.

### Changed
- README: starts with what the library is, when to use it and when not, a picture of the parts, a first run with its output, a table of ways to install, a glossary and the documents by purpose; the description of the API follows unchanged, the status went below it.
- Encoder (`nimgrpc/protobuf`, used by generated code): a `bytes` or `string` field of 64 KiB or more is copied once into a buffer of the size of the message. Before, the buffer was reallocated when the field went in and again when the length in front of it needed more than one byte, so a message with one 4 MiB field cost about 10 MiB while it was encoded. The wire form is the same and generated code does not have to be regenerated. This was the library's part of the pentest's finding 4 (responses a client asks for and never reads): 200 such calls asking for 4 MB responses held 2.53 GB before and 1.76 GB after (measured locally on 2026-11-15, blocking server, release build). What is left is the handler's own message and one encoded copy per waiting handler; [docs/threat-model.md](docs/threat-model.md) says how to bound it. Tests: `tests/tcodec.nim` (suite "large values").

### Fixed
- Blocking server: a unary request much larger than `maxMessage` (6 MB and more against the default 4 MiB) left the client waiting until its deadline, and without a deadline for ever. The server answered RESOURCE_EXHAUSTED when the limit was passed and read no more, so the window of the stream stayed shut and the client could not finish sending to see the answer. The server now resets such a stream with NO_ERROR once its response is complete, as the chronos server already did and as other gRPC servers do; the client gets RESOURCE_EXHAUSTED at once. Found by `tests/tdocs.nim` in CI. Tests: `tests/thostile.nim`.
- Documents that said what the code does not do: [docs/threat-model.md](docs/threat-model.md) said a handler gets the peer's certificate (it gets the metadata only; mutual TLS admits a client, it does not name it); [docs/security-requirements.md](docs/security-requirements.md) said there are no connection quotas (`maxConnections` and `maxConnectionsPerIp` exist since 0.2.0 and 0.4.0); it and `SECURITY.md` called the version 0.0.x.
- README: the health snippet `let health = newHealth()` does not compile beside `import nimgrpc/health` (the name is the module's); it is `let h = newHealth()`.

## 0.5.0 — 2026-11-15

### Security
- TLS: a peer that negotiates no ALPN protocol is refused on both sides. A client that sent no ALPN extension at all (`openssl s_client -tls1_2` without `-alpn`) used to finish the handshake, because BearSSL's own check only fails when a client offers other protocols; the server now ends the handshake with an alert, and a client refuses a server that selects no protocol ("peer did not negotiate ALPN h2"). Resumed sessions are unchanged (found by a local pentest). Tests: `tests/ttls.nim`.
- Both servers: a handler exception that is not a `GrpcError` was sent to the client as UNKNOWN with its text, which can hold file paths, queries and other internals. The client now gets `internal error`. A `GrpcError` keeps its own code and message. New `setErrorHook` (both servers, before `start`) calls a hook with the method path and the exception, so the operator can still log it; without a hook nothing is written anywhere.
- nghttp2: CI, the README and the build pages now use 1.68.1 (was 1.68.0). It fixes CVE-2026-27135 (GHSA-6933-cjhr-5qg6, High): an assertion failure after the session was terminated while handling an ALTSVC, PRIORITY_UPDATE or user-defined extension frame. This library enables none of those frames and never terminates a session from a callback, so a program linked with 1.68.0 is not known to be reachable; rebuild nghttp2 at 1.68.1 all the same. The minimum that compiles stays 1.61.0.
- zlib 1.4 (2026-11-04) fixes several memory errors (CVE-2026-85091 and others) in `gzwrite`, `inflateGetDictionary`, `inflateSync`, `inflatePrime`, `deflatePrime`, `inflateBack`, `gzseek` and `deflateResetKeep`. The library calls none of them (only `deflateInit2`, `deflateBound`, `deflate`, `inflateInit2`, `inflate` and their `End`), so nothing changes here; zlib is the system's and is updated with it.

### Added
- `tools/hostile.sh` (`tools/hostile.py`, `tools/hostiletarget.nim`): a hostile client in raw HTTP/2 frames against the blocking and the chronos server: nested Protobuf groups, a wire type that does not exist, Rapid Reset, CONTINUATION, PING and SETTINGS floods, oversized headers, a 4 GB length prefix, a gzip bomb, random frames, 400 calls opened and left (unary, `Health/Watch`, streaming), 300 MB on a stream nobody reads, 500 idle connections. After each attack an ordinary call must be answered and the server must not have grown past its bound. These are the attacks of the pentest of 2026-11-14, kept so that what they found does not come back.
- `tools/conformance.sh`: h2spec against both HTTP/2 adapters (a failure that is not one of the known ones of [docs/h2spec.md](docs/h2spec.md) fails it) and grpcurl against server reflection.
- The workflow `Hostile client` runs both once a week and when their files change; a failure of the weekly run opens an issue.

### Changed
- Both servers and both clients: the content-type must be `application/grpc`, or that followed by `+` or `;` (`application/grpc+proto`). `application/grpcx` and other look-alikes get HTTP 415 from a server and fail a client call.
- Both servers: a `grpc-timeout` header that is present but malformed (`-1S`, `5x`) ends the call with INTERNAL ("malformed grpc-timeout") before the handler runs; it used to mean no deadline. A call without the header still has no deadline.

## 0.4.0 — 2026-11-15

### Security
- Blocking adapter (server and client): received body bytes were acknowledged to the peer as soon as they arrived, so a stream whose reader did not read grew without limit: 300 MB sent on one `Health/Watch` call, whose handler reads one message and no more, took a server to 587 MB (found by a local pentest, 2026-11-14). Flow control is now manual, as on the chronos adapter: the window of a stream reopens only as its reader takes the bytes (one stream holds at most 1 MiB unread), and the window of the connection reopens at once until 8 MiB wait unread in all its streams.
- Blocking server: a client could use up every worker thread without sending a message. Each call took a worker when its HEADERS arrived, so 400 calls opened and left alone on 4 connections stopped a server with the default 256 workers for everybody (same pentest). A unary call now takes its worker only when its request message has arrived; a call that waits costs no thread. Streaming calls still take a worker from their start; what bounds them is below.
- `Health/Watch` and server reflection on the blocking server keep a worker per call for as long as the client stays: `newHealth(maxWatches = 64)` and `newReflection(maxStreams = 16)` now limit how many run at once (one more gets RESOURCE_EXHAUSTED; 0 for no limit). `Check` and `List` are not limited.

### Added
- CI runs the tests, plain and under AddressSanitizer, on Nim 2.4.0 too (besides 2.2.12 and 2.2.14).
- `Limits.maxCallMs` (both servers; 0, off, by default): the longest a call may last whatever deadline the client asked for. Past it the server resets the call (the handler sees DEADLINE_EXCEEDED, the client CANCELLED). It bounds a streaming call that a client opens and leaves quiet.
- `Limits.maxConnectionsPerIp` (both servers; 0, off, by default): connections served at once from one address; one more is closed at once.
- `tests/thostile.nim`: calls left without a message, large unary messages side by side, `maxCallMs`, the limits of `Watch` and reflection, `maxConnectionsPerIp`; `tests/tblocking.nim`: a stream nobody reads holds one window and the other streams go on.

### Changed
- `Limits.handshakeTimeoutMs` is 20 seconds by default (was 120): on the blocking server a connection costs two threads from the moment it is accepted, and one that sends nothing kept them for two minutes.
- The blocking server no longer ends the program when the system refuses a new thread: the call or the connection waits for a thread that exists.

## 0.3.1 — 2026-11-14

### Security
- `nimgrpc/health`: a request (or, for the client, a response) with a protobuf wire type that does not exist (6 or 7) ended the program with a RangeDefect: the 7-byte body `00 00 00 00 02 0e 00` sent to `/grpc.health.v1.Health/Check` stopped any server that registered the health service, with no authentication. In 0.3.0 only (the service is new there). The decoders now raise `ProtobufError`, which the server answers with INVALID_ARGUMENT.
- A small request could crash a server, or a client reading a reply: the Protobuf decoder had no limit on how deep messages nest. `skipField` skipped a group (an unknown proto2 start-group, two bytes `0xC3 0x3E` for field 1000) by recursing, so a body of such pairs made it recurse once per pair; 200 KB overflowed the stack of a blocking-server worker thread, and `decodeHealthRequest` on 600 KB overflowed the 8 MB main stack, which is where the chronos server runs handlers. Messages nested inside messages (a recursive type such as `message Node { Node child = 2; }`) recursed the same way: `Node.decode` of a 700 000-level chain of 3.5 MB crashed with a segmentation fault (run on the code of 0.3.0, a release build). Every program that decodes Protobuf it did not write is affected, all versions up to 0.3.0: the generated `decode`, the health service, reflection and the well-known types. The message limit (4 MiB by default) did not help, as 2 000 000 groups fit in it. Fixed: decoding stops with `ProtobufError` ("message nested too deeply") past `maxNestingDepth` (100, the limit of protobuf-go and C++ protobuf); a server answers INTERNAL, as for any message it cannot decode. Groups are now skipped without recursion. Generated code needs no regeneration: it reads a nested message through `subReader`, which now carries and checks the depth. Tests: `tests/tcodec.nim` (suite "nesting limit"), `tests/tgrpc.nim` and `tests/tasyncgrpc.nim` (a 200 KB group bomb to a server, then a normal call), and a seed in `tools/fuzz.nim`.

### Added
- TLS: a server dialled by an IP address ("10.0.0.5", "::1", "[::1]"), or with `serverName` an IP address, is checked against the iPAddress entries of its certificate (subjectAltName), as RFC 6125 says; before, only DNS names could be verified, so a service on an address without a name could not use TLS with verification. No SNI is sent for an IP address (RFC 6066). Tests: `tests/ttls.nim`.

### Fixed
- `TlsConfig` shared by several threads: a configuration handed to more than one thread was a Nim `ref` copied between them, and ORC counts references without atomics, so it could be freed while a handshake still read its trust anchors (SIGSEGV in a program that connects afresh from several threads; found by a soak run). The configuration now has an atomic count of owners and each connection holds one. `share(c)` gives a thread or a connection its own object over the same configuration and the same resumable sessions; use it when a `TlsConfig` crosses threads.

## 0.3.0 — 2026-11-09

### Security
- nghttp2 1.61.0 or later is required (was 1.57.0), which limits the CONTINUATION flood (CVE-2024-28182); the build fails with an `#error` against an older header. The limits that nghttp2 applies by default to CONTINUATION frames (8 after a HEADERS frame) and to RST_STREAM (a burst of 1000, then 33 a second: Rapid Reset, CVE-2023-44487) are now set by the library itself, and `tests/th2session.nim` feeds a server the frames of a flood.

### Added
- Happy Eyeballs (RFC 8305) in `dial`, blocking and chronos: the addresses of a name are tried in the order of the resolver's first family, then the families alternating, and when an attempt has not answered within 250 ms (or has failed) the next address is tried alongside it; the first to connect wins. A dead IPv6 route no longer costs a whole `connectTimeoutMs` before IPv4 is tried. Tests: `tests/teyeballs.nim`.
- `unaryCall` (blocking and chronos) sends a call again, up to twice within its deadline (20 ms, then 40 ms apart), when the server refused it without starting on it: REFUSED_STREAM, which is also what nghttp2 reports for a stream a GOAWAY left unprocessed (a draining server, a connection rotated by `maxConnectionAgeMs`, the first burst before SETTINGS). The error of the last attempt has the new `GrpcError.unprocessed` set. Calls that may have run are never repeated, and streaming calls are not retried (`newCall` already tries a fresh connection once). Tests: `tests/tretry.nim`.
- `nimgrpc/reflection`: server reflection (`grpc.reflection.v1` and `v1alpha`) for both servers, so that `grpcurl` and `grpc_cli` can list the services of a server (always) and describe them (with their descriptors): `newReflection()`, `addFileDescriptor`, `srv.register(refl)`. `protoc-gen-nim` writes the serialized `FileDescriptorProto` (without the source info protoc adds) into a module when it runs with `--nim_opt=descriptor`, as the constant `fileDescriptorProto`; the well-known types are built in (`tools/gen_wkt_descriptors.py`). `file_by_filename`, `file_containing_symbol` (messages, nested types, enums and their values, fields, services, methods) answer with the file and the imports the reflection holds; extensions are not supported. Servers gain `serviceNames`. Checked against grpc-go's own reflection client (`tests/interop/reflection_interop.sh`: it builds the descriptors it gets). Tests: `tests/treflection.nim`.
- `nimgrpc/healthclient`: the asking side of the health service, on blocking and chronos channels: `checkHealth` (NOT_FOUND is `hsServiceUnknown`), `isServing`, `waitServing` and `watchHealth` / `next` / `close`. Test: `tests/thealthclient.nim`. The health service is checked against grpc-go's own client (`tests/interop/health_interop.sh`: Check, NOT_FOUND, List, Watch; all pass with grpc-go 1.84.0).
- `nimgrpc/health`: the gRPC health checking service (`grpc.health.v1.Health`: `Check`, `Watch`, `List`) for both servers, which is what the native gRPC probe of Kubernetes, Envoy and `grpc_health_probe` call. `newHealth()`, `srv.register(health)`, `health.setStatus(service, hsNotServing)`, `health.shutdown()` before `stop`. `Health` is a handle to memory shared by all threads (copy it, hand it to threads, `close` frees it). Message bytes checked against `protoc` and the official `health.proto`. Test: `tests/thealth.nim`.
- Rotation of server connections: `Limits.maxConnectionAgeMs` (age, give or take 10%) and `Limits.maxConnectionIdleMs` (no call for that long), both off by default, drain a connection: an advisory GOAWAY, the final one a moment later, the calls in progress finish, then the connection closes; `Limits.maxConnectionAgeGraceMs` (30 s) is how long they get. Behind a load balancer this spreads long-lived clients over new instances and makes them resolve names again (connections are balanced, not calls, in Kubernetes); clients of this library dial a new connection for the next call on their own. Blocking and chronos servers. Tests: `tests/tconnage.nim`, `tests/tconnageasync.nim`.
- TCP keepalive and a limit for the handshake. Every connection, client and server, blocking and chronos, gets the system's TCP keepalive (`Keepalive.tcpSecs`, 15 seconds by default, 0 turns it off): a peer that has vanished is found and a NAT or load balancer does not forget a quiet connection. A server closes a connection whose peer has not completed the TLS handshake and sent its preface and first SETTINGS within `Limits.handshakeTimeoutMs` (120 seconds by default, 0 for no limit); until now such a connection, which holds two threads on the blocking server, stayed until the peer left. Test: `tests/thandshake.nim` (it reads the keepalive timers of the sockets from `/proc/net/tcp`). See [docs/threat-model.md](docs/threat-model.md).
- IPv6. A server listens on an IPv6 address (`address = "::1"`), or on both families (`address = "::"`, dual-stack); the blocking `dial` takes IPv6 literals ("::1", "[::1]") and tries every address a name resolves to, IPv6 ones included, in the resolver's order, each with `connectTimeoutMs`. The `:authority` of an IPv6 host is bracketed. Until now the sockets were IPv4 only: a server could not bind `::1` and a host with only an AAAA record could not be reached. The chronos adapter already resolved both families and now has tests. Test: `tests/tipv6.nim` (skipped without an IPv6 loopback).
- `shutdown(GrpcChannel)`: closes every connection of the channel and frees nothing. Calls in progress, on any thread, fail at once, and new calls are refused. A program whose threads wait in calls can stop them with it, join them, and only then `close` the channel. Safe from any thread and more than once.
- `nimble coverage` / `tools/coverage.sh`: statement coverage of `src/nimgrpc` from gcov (the Nim compiler's `#line` directives make it report `.nim` lines); 88.8% now, CI fails under 80% (job `tests (coverage, Nim 2.2.12)`). See [docs/building.md](docs/building.md).
- The builds of this repository honour `CC`, `CFLAGS` and `LDFLAGS` from the environment (added to the flags in use); see [docs/building.md](docs/building.md), which also says how debug information, repeatable builds and installation are handled.

### Fixed
- Deadlines and timed waits of the blocking adapter counted on `CLOCK_REALTIME`, so a step of the system clock (NTP, a resumed virtual machine) shortened or stretched a timeout. They count on `CLOCK_MONOTONIC` now (Linux; other systems keep the wall clock). Test: `tests/tblocking.nim`, which fails with the old pairing of clocks.
- `close(GrpcChannel)` from one thread while a call of another thread was waiting in `recv` freed the connection under that call: the call that then failed touched freed memory (found with AddressSanitizer in a program that closed its channel to end its reader thread; the corrupted heap ended in a thread spinning for ever in the allocator). `close` now waits (up to ten seconds) for the calls that are inside a procedure of the library on another thread to leave it, and does not free the channel if one does not. A call that has not entered the library yet cannot be waited for: do not start calls on a channel that is being closed. Test: `tests/tchannelclose.nim`.

## 0.1.0 — 2026-11-03

### Changed
- The nimble package is now `nimgrpc` (`nimgrpc.nimble`) and so are the modules: `import grpc` becomes `import nimgrpc`, `import grpc/protobuf` becomes `import nimgrpc/protobuf`, and so on. ## 0.0.2 — 2026-11-03

### Added
- TLS session resumption (session ids), on by default for ten minutes: `setSessionLifetime(config, seconds)`, 0 to turn it off. A reconnect of a channel with the same `TlsConfig` and server name skips the public-key work: new connection plus first call (`tools/hsbench.nim`) 4.9 ms to 0.9 ms with TLS and 6.9 ms to 0.6 ms with mutual TLS. The server keeps only sessions of peers that were authenticated as required, and drops its cache as a whole when the lifetime has passed. A resumed session is not checked against the certificate again, so a revoked or expired certificate keeps working for a peer that holds a session until the lifetime ends (see `docs/security-requirements.md`).
- Scheduled long checks: a weekly mutation fuzzer over the parsers (`tools/fuzz.nim`, `fuzz.yml`), a nightly ThreadSanitizer run of the whole suite (`tsan.yml`) and a weekly heap profile of the server with its summary (`tools/profile.sh`, `profile.yml`). A shared setup action (`.github/actions/setup`) builds nghttp2 and Nim for them.
- Weekly soak test of the chronos server (`tools/soak.sh`, `.github/workflows/soak.yml`): memory per connection and no growth under churn, plain and TLS. `tools/asyncload.nim` gained `hold`, `churn` and `tls` modes.

### Changed
- Cipher order of TLS: the same six suites (ECDHE with AES-128/256-GCM or ChaCha20-Poly1305), now ordered by the CPU. With AES-NI and PCLMULQDQ AES-GCM comes first, which was about 30% faster on large replies in `tools/tlsbench.nim` (33.5 MB/s with ChaCha20, 42-47 MB/s with AES-GCM, loopback, both ends in one process); otherwise ChaCha20 stays first, as BearSSL's portable AES is slow. A server now enforces its own order instead of following the client's. Choose with `cipherOrder` of `tlsServerConfig` / `tlsClientConfig` (`coAuto`, `coAesGcmFirst`, `coChaChaFirst`) or `setCipherOrder`.
- Fewer copies of a message. On receipt `wire.MsgBuf` (replacing `takeFrame` and `appendData`, which were internal) builds the message straight from the chunks as they arrive, instead of collecting them in a buffer and slicing the message out; a declared length reserves nothing, memory grows with the bytes received. On sending, the 5-byte frame prefix goes in front of the message in the stream buffer (`head` of `sendData` / `send`), so `encodeMessage` is no longer called for each message. Measured in pinned runs (`taskset`, `tools/tlsbench.nim`): 64 KiB over TLS about 4% faster, 1 MiB 1-2%, small messages unchanged.
- CI tests on Nim 2.2.12 (the floor of `nimgrpc.nimble`) and 2.2.14; the soak test runs on 2.2.14. Renovate proposes new Nim versions (`renovate.json`), which Dependabot cannot see.

### Fixed
- A new TLS connection took about twice as long as it had to: BearSSL's "full" profiles verify certificate signatures with the generic prime_i31 code, which was about 60% of a handshake. Certificates and the handshake now use the fast P-256 code (m64 where the CPU has 64x64->128 multiplication, m31 otherwise). New connection plus first call, `tools/hsbench.nim`: TLS 7.7 to 4.2 ms, mutual TLS 9.5 to 5.7 ms.
- The blocking transport woke every thread of a connection on each change (one condition variable for the writer, the senders and the receivers) and sent each piece of output with its own `send`. The writer now has its own condition, wakes happen only when someone waits, and what is ready is sent in one `send`. For a 1 KiB unary call: `futex` calls 60 to 26, `sendto` 6 to 2.3 and `recvfrom` 4.7 to 2.3.
- Bulk data was copied byte by byte, which a profile of a 900 KB echo over TLS showed to be about 72% of the CPU time (AES-GCM itself was about 4%). Appending to the connection, stream and TLS buffers, taking messages out of them and reading TLS plaintext now use one `copyMem` and no longer zero the space they grow into (`src/grpc/bytebuf.nim`). The TLS pumps also stopped shifting the whole pending buffer after every 16 KiB record (quadratic in the message size) and drop two more copies per message (`takeOutputInto`, reading BearSSL output straight into the buffer). In `tools/tlsbench.nim` (1 MiB replies, loopback) TLS went from about 48 MB/s to 136-194 MB/s and plaintext from 108-153 to 237-293 MB/s.
- The chronos transport copied each message element by element at every `async` layer (chronos copies the arguments of an `async` proc into its frame, and `await` hands out a borrowed value): a profile of a 1 MiB echo over TLS on the event loop showed 41% of the time in `seq[byte]` copies. `send` of the async client, server and `AsyncH2Stream` now takes the message as `sink`, puts the 5-byte frame prefix in front in the stream buffer and moves the message into the waiting job only when the buffer is full; `unaryCall` and the unary handler path move replies instead of copying them. `tools/asyncbench.nim`, pinned to 4 cores, one thread for both ends: 1 MiB replies plain 315 to 693 MB/s, over TLS 243 to 415 MB/s; 64 KiB over TLS 242 to 398 MB/s; 1 KiB calls about 5% faster (latency, not copies).
- Every connection advertised the default HTTP/2 window of 64 KiB per stream and per connection, so a large message waited for the peer's WINDOW_UPDATE every 64 KiB, each one a hand-off between threads and a few system calls. A session now announces a window of 1 MiB for each stream and for the connection (`receiveWindow`, `src/grpc/h2/session.nim`), which is also the most unread data a peer can make us hold per connection. CiNim's `shimtransport` (loopback, pinned): 900 KB requests 4.5 to 2.8 ms, 64 KiB 0.34 to 0.28 ms, CPU of the client and the server for the series about 1.1 to 0.85 s (ZeroMQ + CURVE 0.7-0.8 s); `futex` calls of the client for 200 requests of 900 KB 139 000 to 62 000. A larger maximum frame size and a larger socket read buffer were tried and gave nothing.
- A client that sent a large message to a call the chronos server had already ended without reading the request waited forever: the server never told it to stop. The server now resets such a stream with NO_ERROR once its response is complete (as other gRPC servers do), and the client's `send` raises the server's status.
- `dial` and `dialAsync` blocked on connect for as long as the system's TCP timeout (minutes), with no way to bound it. Each connection attempt now gets `connectTimeoutMs`, 20 seconds by default; past it the call fails with UNAVAILABLE. A negative value keeps the old behaviour. Resolving the host name is not covered by the timeout.

## 0.0.1 — 2026-11-02

### Security
- TLS is narrowed to what is safe: only ECDHE key agreement with AES-GCM or ChaCha20-Poly1305 (BearSSL's "full" profile also offered static RSA, CBC and 3DES), RSA certificate keys of 2048 bits or more (the default admitted 1017), and no MD5 or SHA-1 certificate signatures. A peer that supports nothing better cannot connect any more; see [docs/upgrading.md](docs/upgrading.md).

### Added
- Manual HTTP/2 flow control on the chronos adapter: the peer's window reopens only as handlers read, so a slow reader backpressures the sender instead of buffering without bound.
- Project documents for the OpenSSF Best Practices levels: [security policy](SECURITY.md), [governance](GOVERNANCE.md), [contributing](CONTRIBUTING.md), [code of conduct](CODE_OF_CONDUCT.md), DCO sign-off with a check of pull requests, [threat model](docs/threat-model.md), [architecture](docs/architecture.md), [assurance case](docs/assurance-case.md), [security requirements](docs/security-requirements.md), [security policies](docs/security-policies.md), [building](docs/building.md), [roadmap](docs/roadmap.md), [upgrading](docs/upgrading.md).
